## 1. Product Goal

V1 คือเกมจำลองชีวิตคนไทยแบบเล่นคนเดียว โดยผู้เล่นเริ่มจากการเกิดในครอบครัวหนึ่ง เติบโตผ่านช่วงวัย เผชิญเหตุการณ์ ตัดสินใจด้านการเรียน งาน ความสัมพันธ์ และการเงิน ก่อนจบชีวิตและสรุปผลลัพธ์ของชีวิตนั้น

**นิยามความสำเร็จของ V1:** ผู้เล่นใหม่สามารถเริ่มเกม เล่นผ่านช่วงวัยและระบบสำคัญได้อย่างต่อเนื่อง จนถึงฉากจบ โดยไม่ติด Softlock ไม่สูญเสียความคืบหน้าจาก Save/Load และเข้าใจผลของการตัดสินใจหลักได้

V1 ให้ความสำคัญกับความสมบูรณ์ของวงจรการเล่น ความสมดุล และความเสถียร มากกว่าปริมาณฟีเจอร์หรือจำนวน Event ที่เพิ่มขึ้น

| วงจรชีวิต | อายุ ช่วงวัย ปีปัจจุบัน การเปลี่ยนปี ลำดับเทิร์น และเงื่อนไขจบชีวิต |

| Ending & Legacy | เงื่อนไขการเสียชีวิต ฉากจบ การสรุปชีวิต พินัยกรรม มรดก และการเริ่มรุ่นถัดไป |

## 3. ขอบเขตที่ไม่ทำใน V1

รายการต่อไปนี้ให้เลื่อนไปหลัง V1 เว้นแต่พบว่าเป็นเงื่อนไขจำเป็นต่อการเล่นจบ:

- Multiplayer, PvP, ระบบเพื่อน/แชต และระบบบัญชีผู้เล่นออนไลน์
- Cloud Save และการซิงก์ข้ามอุปกรณ์
- AI สร้าง Event หรือเนื้อหาแบบอิสระขณะเล่น
- เศรษฐกิจมหภาคที่จำลองทั้งประเทศหรือระบบจำลองตลาดการเงินจริงแบบละเอียด
- ระบบ Mod และเครื่องมือสร้าง/แชร์ฐานข้อมูลสำหรับผู้เล่น
- การเพิ่ม Event จำนวนมากโดยไม่ผ่านการทดสอบความซ้ำซ้อนและสมดุล
- การรื้อ UI ทั้งหมดเพื่อความสวยงาม หากไม่มีปัญหาการใช้งานหรือความเสถียรที่ชัดเจน

## 4. กติกาการออกแบบที่ล็อกไว้

### 4.1 ช่วงวัยไม่ใช่ Life Path

ข้อมูลปัจจุบันมีช่วงวัย 6 ช่วง ได้แก่ 0–4, 5–12, 13–17, 18–35, 36–59 และ 60–100 ปี ช่วงวัยเหล่านี้ใช้ควบคุมพัฒนาการและคุณสมบัติของ Event

Life Path เป็นอีกแนวคิดหนึ่ง: ต้องสะท้อนทิศทางหรือรูปแบบการใช้ชีวิตที่ผู้เล่นกำหนด และมีผลต่อโอกาส ทางเลือก หรือเหตุการณ์ในระยะยาว การมี `lifePhaseId` จึงยังไม่ถือว่าได้ส่งมอบ Life Path แล้ว

### 4.2 Event Pool

ระบบปัจจุบันมีการคัด Event จากถัง life-phase, career, relationship และ location/karma ด้วยการสุ่มแบบถ่วงน้ำหนัก พร้อม fallback ตามเงื่อนไขอายุและความพร้อมของผู้เล่น ขั้นต่อไปต้องพิจารณาการเชื่อม Life Path เข้ากับโครงสร้างนี้ โดยไม่ทำให้ Event ที่มีอยู่หายไปหรือถูกแทนที่โดยไม่ตั้งใจ

### 4.3 Choice ต้องมีความหมาย

- ไม่บังคับให้ทุก Event มี Choice 3 ข้อ หากเนื้อหาไม่รองรับ
- Choice ควรมี trade-off, ความเสี่ยง, ค่าใช้จ่าย หรือผลระยะยาวที่ต่างกันเมื่อเหมาะสม
- แสดงเงื่อนไขที่ผู้เล่นจำเป็นต้องรู้ เช่น ค่าใช้จ่ายหรือข้อกำหนด แต่ไม่จำเป็นต้องเปิดเผยตัวเลขผลลัพธ์ภายในทั้งหมดก่อนตัดสินใจ
- หลีกเลี่ยง Choice ที่เป็นเพียงการกดรับผลบวกโดยไม่มีต้นทุนหรือผลตามมา

### 4.4 เศรษฐกิจและครอบครัว

ต้องแยกความหมายของเงินในกระเป๋าผู้เล่น เงินออมวัยเด็ก เงินสนับสนุนรายปีจากพ่อแม่ และความมั่งคั่งของครอบครัวให้ชัดเจน การสนับสนุนจากครอบครัวไม่ควรถูกตีความว่าเป็นทรัพย์สินส่วนตัวของผู้เล่นโดยอัตโนมัติ

เงินสนับสนุนและความสามารถในการช่วยเหลือควรสัมพันธ์กับฐานะครอบครัว อายุ และเงื่อนไขความสัมพันธ์/การเลี้ยงดู การออกแบบตัวเลขต้องผ่านการจำลองสถานการณ์และ Playtest ก่อนล็อกค่าจริง

### 4.5 Audio

ยึดแนวทาง Hybrid ที่เลือกไว้: ใช้ Synth สำหรับเสียง UI ทั่วไป และใช้ MP3 สำหรับเสียงเฉพาะเหตุการณ์ที่ต้องการเอกลักษณ์ โดยรักษา BGM เดิมไว้ในช่วงแรกของการปรับระบบ และไม่เพิ่มไฟล์เสียงจำนวนมากก่อนกำหนดระดับเสียง/การทำงานบนมือถือ

## 5. ลำดับการทำงานหลัง Design Freeze

| Phase | เป้าหมาย | ผลลัพธ์หลัก |
|---|---|---|
| 5A | Design Freeze & V1 Scope Lock | Scope, Acceptance Criteria, System Audit |
| 5B | Core Balance | ปรับเศรษฐกิจ สถานะ Trait/Status และการสนับสนุนจากครอบครัว |
| 5C | Life Path Integration | นิยามข้อมูลและเชื่อมเส้นทางชีวิตกับระบบเกม |
| 5D | Event & Narrative Rework | เพิ่มคุณภาพ Choice, trade-off, ผลระยะยาว และความหลากหลาย |
| 5E | Full-life Integration & QA | ทดสอบการเล่นต่อเนื่องตั้งแต่เกิดจน Ending และรุ่นทายาท |
| 5F | Audio System Rework | Hybrid Audio, Mixer, Settings และ Audio Regression |
| 5G | Release Preparation | Save/Load hardening, mobile/browser checks, documentation และ release checklist |

ลำดับนี้เป็นการจัดงานเพื่อส่งมอบ V1 ไม่ใช่คำมั่นว่าจะเพิ่มระบบใหม่ทุก Phase หากการตรวจสอบพบว่าระบบใดมีอยู่แล้ว ให้ทดสอบและปรับปรุงแทนการเขียนใหม่

## 6. เงื่อนไขเปลี่ยน Scope

หลังเอกสารนี้ถูก Merge แล้ว ให้ถือ Scope เป็น baseline ของ V1 การเปลี่ยนขอบเขตทำได้เมื่อ:

1. พบ Bug หรือช่องโหว่ที่ขัดขวางการเริ่มเกม เล่นต่อ หรือจบชีวิต
2. Acceptance Criteria ข้อใดทำไม่ได้ด้วยโครงสร้างปัจจุบัน
3. ผล Playtest แสดงปัญหาที่กระทบประสบการณ์หลักอย่างชัดเจน
4. มีการตัดสินใจอย่างชัดเจนว่าจะเลื่อนหรือถอดฟีเจอร์ใด

ทุกการเปลี่ยนต้องบันทึกเหตุผล ผลกระทบ และเกณฑ์ทดสอบใหม่ ห้ามเพิ่ม Feature เพียงเพราะทำได้หรือดูน่าสนใจ
